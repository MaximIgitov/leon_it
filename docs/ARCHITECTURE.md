# Архитектура LeonIT

Что из чего состоит, как данные проходят путь «вакансия → ссылка → интервью →
заключение → решение» и какие решения приняты осознанно. План и границы — в
[ROADMAP.md](ROADMAP.md), эксплуатация — в [RUNBOOK.md](RUNBOOK.md), детали
модулей бэкенда — в `backend/README.md`.

## Обзор

```
кандидат ──HTTPS──▶ frontend (TanStack Start) ──/api──▶ api (FastAPI) ──▶ PostgreSQL
                       │                          │      ▲
                       │  подписанные ссылки      │      │ jobs (таблица-очередь)
                       ▼                          ▼      │
                    /data/media ◀── worker ── ffmpeg ── модели (STT · LLM · TTS)
```

* **frontend** — кабинет рекрутера/менеджера, комната интервью, лендинг,
  публичный отчёт по ссылке. TanStack Start, React 19, TypeScript, Tailwind CSS 4,
  HeroUI 3; тема LeonIT (зелёный, абрикосовый и тёплый коричневый, Nunito).
  Визуальные правила и токены — [DESIGN.md](DESIGN.md).
* **api** — модульный монолит на FastAPI: аккаунты и роли, вакансии, кандидаты
  и интервью, комната, отчёты, оценка, ассистент, публичный API, интеграции.
* **worker** — тот же образ, другой entrypoint: обработка медиа, оценка,
  письма, синхронизации, чистка по сроку хранения.
* **PostgreSQL 16** — данные и очередь задач; **локальный том** — медиа.
* **Caddy** — HTTPS (Let's Encrypt на `leon-it.tech`; `www` перенаправляется,
  старый `<ip>.sslip.io` остаётся алиасом для разосланных ссылок), проксирует `/api/*`
  на api, остальное — на frontend. Один origin: cookie/CORS не нужны.

## Бэкенд: модульный монолит

Каждая предметная область — пакет `backend/leonit/<area>/` со слоями
`models.py` (SQLAlchemy 2, async), `schemas.py` (Pydantic v2), `service.py`
(логика, работает с сессией), `router.py` (FastAPI, только транспорт). Общая
инфраструктура — `leonit/core/`: настройки (pydantic-settings, валидаторы
production), БД и миграции, ошибки → HTTP, наблюдаемость (request_id, метрики),
rate limit, `Storage`, шифрование секретов (`crypto.py`), матрица прав
(`authz.py`).

Реестры вместо магии: роутеры перечислены в `main.py`, модели — в `models.py`
(`MODEL_MODULES`), обработчики задач — в `jobs/registry.py`
(`JOB_HANDLER_MODULES`). Новый модуль подключается одной строкой в каждом.

| Область | Ключевое |
|---|---|
| `accounts` | организации, пользователи, роли owner / recruiter / hiring_manager (scope по вакансиям), приглашения по ссылке с отзывом, `token_version` для отзыва сессий, аудит |
| `vacancies` | вакансия, требования и навыки, рубрика компетенций с весами и якорными уровнями 1–4, вопросы (`video` / `code`) с лимитами, генерация и вычитка вопросов моделью, публикация |
| `candidates` | кандидаты, приглашения-ссылки (токен хранится хешем), state machine интервью с таймстемпами, согласия с версиями документов и журналом |
| `interviews` | комната: старт, показ вопроса, серверные тайминги, запись ответов чанками с докачкой, события клиента, завершение |
| `pipeline` | ffprobe → извлечение аудио → ремукс → STT с таймкодами; compare-and-set захват ответа, устойчивость к отмене и брошенным задачам; срок хранения и удаление |
| `evaluation` | заключение по рубрике с цитатами, детерминированная рекомендация, редактирование ПДн, проверка цитат, защита от инъекций, eval-контур с датасетом |
| `reports` | карточка кандидата, ранжирование, заметки и решение ревьюера, ссылки для нанимающего менеджера (срок, продление, отзыв, аудит просмотров) |
| `notifications` | outbox писем, SMTP/консоль, вкладка «Письма», напоминания, «отчёт готов», growth-письмо, отписка |
| `assistant` | агент с инструментами и предложениями (proposal) для необратимых действий, SSE-стрим, подсказки под роль; инструмент поиска по базе знаний |
| `knowledge` | база знаний организации: разбор txt/md/html/pdf/docx/csv/xlsx/json, фрагменты, BM25 с лёгким стеммингом, контекст компании для промптов |
| `api_tokens` + `public_api` | токены `leonit_<random>` с областями (SHA-256 в БД), `/api/v1`, документация Scalar |
| `hh`, `huntflow` | OAuth HH.ru, импорт вакансий и откликов, диалог с кандидатом до ссылки; передача кандидата и отчёта в Huntflow; fake-режимы на фикстурах |
| `integrity` | достоверность записи: правила по событиям и метаданным, вердикты ревьюера, метрика флагов |
| `avatar` | ИИ-аватар интервьюера: протокол провайдера, HeyGen (кошелёк pay-as-you-go, `Idempotency-Key`), кэш клипов в хранилище, задача `avatar.prewarm` при публикации; включается в настройках вакансии |
| `code_runner` | интерфейс раннера кода за фиче-флагом — задел |
| `demo` | сид демо-организации из eval-датасета и документы базы знаний о Example IT |

## Данные

PostgreSQL на стенде и в CI (отдельный job: `alembic upgrade head` + `alembic
check` на чистой базе + прогон тестов), SQLite — локально и в быстрых тестах.
Миграции Alembic обязательны для каждой модели; тест
`test_migrations_apply_on_fresh_database` не даёт забыть.

Файлы — через абстракцию `Storage` (локальный том сейчас, S3 — замена одного
класса). Наружу файлы отдаются только подписанными короткоживущими URL с
поддержкой `Range` (перемотка видео); том никогда не публикуется как статика.

Секреты интеграций (OAuth-токены, ключи API) — только в зашифрованном виде
(Fernet, `DATA_ENCRYPTION_KEY`, ротация через вторичные ключи).

## Фоновые задачи

Таблица `jobs`: захват `SKIP LOCKED` + аренда с heartbeat, повторы с
экспоненциальной паузой, `dedupe_key` (одна активная задача на сущность),
ресурсы-семафоры (`ffmpeg` — 1, `llm` — 3, `default`), graceful shutdown с
возвратом задач в очередь. Хуки воркера: `on_worker_start` (поставить
периодическую задачу) и `on_worker_tick` (раз в час — страховка расписаний,
возврат брошенных ответов в очередь). Шаги обработчиков идемпотентны, статус
виден в карточке кандидата, есть кнопка «Переобработать».

## Модели

OpenAI-совместимый шлюз с конфигурацией на роль (`MODEL_<ROLE>_BASE_URL /
_API_KEY / _MODEL / _PROXY_URL`): `evaluator`, `assistant`, `interviewer`,
`stt`, `tts`. По умолчанию — AI Tunnel (доступен из РФ, умеет `/audio/*`);
роли можно развести по разным провайдерам, прокси задаётся на роль.
Structured output — JSON по схеме Pydantic с одним repair-ретраем, сырой ответ
и usage сохраняются. Ретраи, таймауты и breaker на провайдера. Кэш TTS по хешу
текста и голоса. `MODEL_PROVIDER=fake` — детерминированный провайдер для CI,
e2e и демо без ключей.

Безопасность промптов: перед отправкой в модель ФИО, e-mail и телефоны заменяются
плейсхолдерами; транскрипты уходят в секциях с маркерами, содержащими случайный
код сеанса, строки данных помечены префиксом, похожие на разделители
последовательности обезвреживаются; модель предупреждена, что внутри — данные,
а не инструкции. Цитаты заключения сверяются с транскриптом и помечаются
`verified`.

## Поток интервью

1. Рекрутер публикует вакансию (требования, рубрика, вопросы) и приглашает
   кандидата — письмо со ссылкой `/i/<token>` (токен ≥ 128 бит, в БД — хеш).
2. Кандидат: имя, e-mail, согласия (версии документов фиксируются), проверка
   камеры и микрофона (матрица браузер/ОС, уровень микрофона, пробная запись),
   тренировочный вопрос.
3. Комната: вопрос показывается и озвучивается (TTS), сервер фиксирует время
   показа; `MediaRecorder` пишет ответ (каскад MIME: VP9/VP8+Opus, H.264/AAC),
   чанки загружаются строго последовательно с докачкой по смещению; лимиты и
   перезаписи — из настроек вакансии; события клиента (уход с вкладки, вставка,
   смена устройства) приходят батчами с таймкодами.
4. После каждого ответа — задача `answer.process`: ffprobe (кодеки, теги
   «чем записано»), извлечение аудио (Opus копируется, остальное → моно 16 кГц),
   ремукс WebM для перемотки, STT с подсказкой из навыков вакансии.
5. После завершения — `interview.process`: ждёт транскрипты, редактирует ПДн,
   вызывает оценщика, считает `fit_score` по рубрике и рекомендацию по порогам,
   проверяет цитаты, сохраняет заключение, при настройке — готовит обратную
   связь кандидату; уведомляет рекрутера и менеджеров.
6. Если у вакансии включены уточняющие вопросы, перед финалом система собирает
   финальный блок: модель роли `interviewer` придумывает до `followups_max`
   уточнений по ответам, где рекрутер это разрешил и уже есть транскрипт.
   Ждать транскрипты бесконечно нельзя, поэтому у комнаты есть бюджет
   ожидания; ответ на уточнение связывается с исходным.
7. Рекрутер и нанимающий менеджер (по ссылке с ограниченным доступом) смотрят
   карточку: видео с перемоткой по цитатам, транскрипт, заключение, заметки,
   принимают решение; кандидат получает growth-письмо по настройке вакансии.

## Безопасность

JWT с `token_version` (выход со всех устройств, отзыв доступа), матрица
роль × ресурс × действие в одном месте (`core/authz.py`) с тестами,
scope нанимающего менеджера по вакансиям, ссылки-токены для кандидатов и
отчётов (хеш в БД, срок, отзыв, аудит просмотров), API-токены с областями и
rate limit, security-заголовки, `noindex`/`no-referrer` на страницах кандидата
и отчёта, журнал согласий, срок хранения медиа и удаление данных кандидата,
шифрование секретов интеграций, CSP и SRI на странице документации API.

## Что решено не делать (и почему)

Перекодирование видео на сервере (дорого, не нужно для оценки), детекция
«ИИ-текста»/липсинк/анализ взгляда и любая идентификация личности (ненадёжно и
этически спорно — integrity показывает факты, решение принимает человек),
локальные модели (стенд слабый), refresh-токены с серверным хранением (вместо
них короткий JWT + `token_version`).
